## 1. 프로젝트 소개

### 1.1 한 줄 소개
발표 영상을 업로드하면 AI가 이를 분석하고, 실시간 Q&A 세션을 통해 꼬리 질문과 답변 훈련을 이어가며, 최종 리포트까지 생성하는 발표 코칭 시스템입니다.

### 1.2 프로젝트 성격
이 프로젝트는 단순한 발표 점검 도구가 아니라, 아래 3단계를 하나로 연결한 **훈련형 코칭 제품**입니다.

- **분석**: 발표 내용, 속도, 군더더기, 논리 구조를 확인
- **훈련**: AI가 질문을 던지고 사용자가 답변하는 실전형 Q&A
- **정리**: 전체 결과를 종합해 리포트 제공 및 임시 데이터 정리

### 1.3 주요 사용자
- 발표 연습이 필요한 학생
- 취업 준비 중인 면접/PT 사용자
- 실전 질문 대응력을 높이고 싶은 발표자
- 반복 훈련 기반 피드백을 원하는 사용자

### 1.4 저장소 구성
루트 저장소는 현재 두 개의 구현 영역을 가진 통합 구조입니다.

- `frontend`: 사용자 인터페이스, 세션 UI, 업로드 및 Q&A 화면
- `backend`: 영상 분석, AI 질문 생성, 답변 피드백, 리포트 생성

## 2. 제품 목표와 문제 정의

### 2.1 해결하려는 문제
일반적인 발표 연습은 대개 다음 한계가 있습니다.

1. 발표를 녹화해도 무엇이 문제인지 정확히 알기 어렵다.
2. 피드백이 한 번의 분석으로 끝나기 때문에 행동 변화로 이어지기 어렵다.
3. 실제 질문에 대한 대응 연습이 부족하다.
4. 결과가 쌓이지 않아 성장 과정을 추적하기 어렵다.

### 2.2 제품 목표
이 제품의 목표는 발표 훈련을 **반복 가능한 루틴**으로 바꾸는 것입니다.

- AI가 발표를 분석한다.
- 분석 결과를 바탕으로 실전형 질문을 이어간다.
- 답변을 즉시 피드백한다.
- 최종적으로 개인별 개선 포인트를 리포트로 정리한다.

### 2.3 경험 설계 원칙
- 사용자는 복잡한 설정 없이 바로 연습을 시작할 수 있어야 한다.
- 핵심 행동은 업로드, 확인, 답변, 제출 정도로 단순해야 한다.
- AI의 역할은 과시가 아니라 **훈련의 흐름을 자연스럽게 이어주는 것**이어야 한다.
- 세션이 끝나면 데이터가 정리되어야 한다.

## 3. AI와 함께 정리한 기획문서

이 섹션은 실제 구현 방향을 정리한 내부 기획 문서입니다.

### 3.1 제품 정의
이 제품은 발표자에게 **분석 결과를 즉시 행동으로 연결하는 훈련 환경**을 제공하는 AI 발표 코칭 플랫폼입니다.  
단순한 피드백 출력이 아니라, AI가 질문을 던지고 사용자가 답하는 반복 훈련을 통해 실전 감각을 키우는 것이 핵심입니다.

### 3.2 해결하려는 문제
- 발표 연습이 녹화 확인에서 끝나기 쉽다.
- 사용자가 무엇을 고쳐야 하는지 명확하게 알기 어렵다.
- 실제 질의응답 상황을 반영한 훈련이 부족하다.
- 분석 결과와 실전 훈련이 분리되어 학습 효과가 떨어진다.

### 3.3 핵심 목표
- 업로드한 발표 자료를 AI가 자동 분석한다.
- 분석 결과를 기반으로 실전형 Q&A 훈련을 제공한다.
- 답변에 대한 피드백과 다음 질문을 하나의 턴으로 연결한다.
- 훈련 종료 후 종합 리포트를 제공한다.
- 세션 파일이 서버에 남지 않도록 정리한다.

### 3.4 사용자 플로우
| 단계 | 사용 화면 | 사용자가 하는 일 | 시스템 역할 |
|---|---|---|---|
| 1 | 업로드 | 발표 영상 선택 | 파일 검증, 세션 생성, 분석 요청 |
| 2 | 분석 | 결과 확인 | 발표 스크립트/지표 제공 |
| 3 | Q&A | AI 질문에 답변 | 질문 생성, 타이머, 답변 제출 |
| 4 | 리포트 | 최종 결과 확인 | 분석 + Q&A 종합 피드백 제공 |
| 5 | 정리 | 세션 종료 | 임시 파일 삭제 |

### 3.5 화면/라우트 설계
#### 프론트엔드
- `/dashboard`
- `/upload-training`
- `/analysis?sessionId=...`
- `/ai-qa-session?sessionId=...`
- `/reports?sessionId=...`

#### 백엔드 API
- `POST /api/v1/presentation/analyze`
- `POST /api/v1/roleplay/start`
- `POST /api/v1/roleplay/turn`
- `POST /api/v1/report/generate`
- `DELETE /api/v1/session/cleanup`

### 3.6 기능 범위
#### 포함
- 영상 업로드 및 분석
- AI 질문 생성 및 답변 턴 처리
- 분석 결과 및 종합 리포트 제공
- 세션 복원 및 임시 파일 정리

#### 제외 또는 후순위
- 데모 모드 기반 mock 분기
- 복잡한 협업 기능
- 다중 사용자 실시간 편집

### 3.7 완료 기준
- 업로드 → 분석 → Q&A → 리포트 흐름이 끊기지 않는다.
- 세션 ID 기준으로 프론트와 백엔드가 자연스럽게 연결된다.
- AI 응답이 불완전해도 서비스가 쉽게 무너지지 않는다.
- 세션 종료 시 임시 파일이 남지 않는다.

## 4. 시스템 구조

### 4.1 전체 흐름
1. 프론트엔드가 사용자의 발표 영상을 업로드한다.
2. 백엔드가 업로드된 파일을 세션 단위로 저장하고 분석한다.
3. 분석 결과는 프론트엔드로 전달되어 UI에 표시된다.
4. 사용자가 Q&A 세션으로 진입하면 백엔드는 질문 생성과 답변 피드백을 반복한다.
5. 최종 리포트 생성 후 세션 정리 API로 임시 파일을 제거한다.

### 4.2 세션 중심 설계
이 프로젝트는 모든 흐름을 `sessionId` 기준으로 연결합니다.

- 업로드 결과와 분석 결과를 묶는다.
- Q&A 히스토리를 세션과 연결한다.
- 리포트 생성 시 이전 분석과 대화 이력을 함께 사용한다.
- 세션 종료 시 정리 대상 파일을 명확하게 찾을 수 있다.

### 4.3 책임 분리
#### Frontend
- 사용자 입력
- UI 상태 관리
- API 요청 트리거
- 결과 표시 및 화면 전환

#### Backend
- 파일 업로드 처리
- Gemini 분석 및 질의 생성
- TTS 생성 및 Base64 반환
- 리포트 계산 및 세션 파일 정리

## 5. 프론트엔드 상세

### 5.1 프론트엔드 역할
프론트엔드는 사용자가 보는 전체 경험을 담당합니다.

- 발표 업로드 화면 제공
- 분석 결과 표시
- Q&A 세션 인터페이스 제공
- 리포트 확인 화면 제공
- 세션 복원 및 라우팅 연결

### 5.2 주요 기술
- React
- Vite
- TypeScript
- TailwindCSS
- Zustand
- React Query
- React Router
- Axios

### 5.3 주요 파일/구조
- `src/App.tsx`: 라우터 진입점
- `src/pages/UploadTrainingPage.tsx`: 업로드 화면
- `src/pages/AiQaSessionPage.tsx`: AI Q&A 화면
- `src/pages/AnalysisPage.tsx`: 분석 결과 화면
- `src/pages/ReportsPage.tsx`: 최종 리포트 화면
- `src/api/qa.ts`: QA 관련 API 및 mutation 훅
- `src/features/ai-qa-session/store/useAiQaSessionStore.ts`: QA 세션 상태 저장소

### 5.4 프론트엔드 개발 원칙
- 페이지는 오케스트레이션에 집중한다.
- 도메인 상태는 store 또는 feature로 분리한다.
- 서버 상태는 React Query로 관리한다.
- 삭제된 컴포넌트/타입/import가 남지 않도록 정리한다.
- UX는 단순하고 명확하게 유지한다.

## 6. 백엔드 상세

### 6.1 백엔드 역할
백엔드는 AI 분석과 질의응답 생성의 핵심 엔진입니다.

- 발표 영상 분석
- 첫 질문 생성
- 답변 분석 및 다음 질문 생성
- 종합 리포트 생성
- 세션 임시 파일 정리

### 6.2 주요 기술
- FastAPI
- Uvicorn
- Google Gemini 2.5 Flash
- gTTS
- Pydantic
- Python 3.12

### 6.3 주요 파일/구조
- `main.py`: FastAPI 앱, 스키마, 엔드포인트
- `requirements.txt`: 의존성 목록
- `temp_sessions/`: 세션별 임시 저장소

### 6.4 백엔드 설계 포인트
- 멀티모달 입력을 직접 처리한다.
- Gemini 응답이 JSON 형식을 벗어나도 복구하도록 방어한다.
- 업로드 파일과 Gemini 임시 파일을 모두 정리한다.
- TTS 오디오는 Base64로 내려 프론트 연동을 단순화한다.

### 6.5 API 요약
- `POST /api/v1/presentation/analyze`
- `POST /api/v1/roleplay/start`
- `POST /api/v1/roleplay/turn`
- `POST /api/v1/report/generate`
- `DELETE /api/v1/session/cleanup`

## 7. 개발 지침서

### 7.1 폴더 구조 원칙
#### Frontend
- `src/pages`: 라우트 단위 화면
- `src/components`: 재사용 UI와 레이아웃
- `src/api`: API 클라이언트 및 도메인 API
- `src/features`: 도메인 상태와 로직
- `src/store`: 전역 상태
- `src/hooks`: 공통 훅
- `src/types`: 공통 타입

#### Backend
- `main.py`: FastAPI 앱 및 라우트 정의
- `requirements.txt`: Python 의존성
- `temp_sessions/`: 세션 임시 저장소

### 7.2 상태 관리 원칙
- 서버 상태는 React Query로 관리한다.
- 화면/세션 상태는 Zustand로 관리한다.
- 페이지에서는 selector 기반 구독을 우선한다.
- 불필요한 전역 상태는 만들지 않는다.

### 7.3 API 연동 원칙
- 공통 요청 처리는 `frontend/src/api/client.ts`에서 담당한다.
- QA 관련 요청/뮤테이션은 `frontend/src/api/qa.ts` 중심으로 관리한다.
- 백엔드는 Gemini 응답을 JSON으로 강제하고, 파싱 실패를 방어한다.
- 프론트와 백엔드의 요청/응답 필드명은 항상 일치시킨다.

### 7.4 에러 처리 원칙
- 에러 메시지는 기술 정보보다 사용자 행동 중심으로 작성한다.
- 최소한 다음 행동을 제공한다.
  - 다시 시도
  - 세션 복구
  - 이전 화면으로 이동
- JSON 파싱 실패, 필수 입력 누락, 파일 업로드 실패를 명확하게 구분한다.

### 7.5 UI/UX 원칙
- 한 화면의 핵심 행동은 1~2개로 제한한다.
- 상태 라벨은 내부 상태명보다 사용자 관점 표현을 우선한다.
- 중복 패널보다 단일 흐름 중심의 레이아웃을 사용한다.
- 업로드/분석/Q&A는 사용자가 다음 행동을 바로 알 수 있게 설계한다.

### 7.6 백엔드 운영 원칙
- 세션별 임시 파일은 반드시 정리한다.
- Gemini 업로드 파일과 로컬 파일을 모두 삭제한다.
- `temp_sessions/`에 파일이 쌓이지 않는지 수시로 확인한다.
- `history_context` 같은 폼 필드는 기본값을 두어 422 오류를 방지한다.

### 7.7 유지보수 원칙
- 새 기능 추가 시 프론트/백엔드 README를 함께 갱신한다.
- API 변경 시 프론트 요청/응답 타입을 점검한다.
- 삭제한 파일의 import가 남지 않았는지 확인한다.
- 빌드와 실행 검증 후 병합한다.
